# TurretProto Compute - review and integration plan

Reviewed 9/7/2026. Static read of the whole folder, no builds (no cargo or octave on this box).

## What is in here

Three pieces that do not talk to each other, plus hardware notes.

1. `.338NM Ballistic Solver` - Python/FastAPI + Vite/React. G7 RK4, atmosphere,
   Coriolis, spin drift (Litz), Miller SG, BC truing, bullet library.
2. `ballistics` - the Rust port. Cleaner and faster, no_std capable, wasm build.
   Feature regressed vs the Python: no spin drift, no SG, no truing, no bullet library.
3. `Point Vector Stabilization Controller Base` - MATLAB. 1-axis and 2-axis
   gimbal plant, cascade position/rate loop, PID and LADRC rate controllers.
4. `Turretnoteshardware.txt` - Jetson Orin Nano, then IMU + brushless gimbal +
   recoil actuator, then DuraCOR.

What is not in here: the tracker/estimator, anything that turns a target into a
gimbal setpoint, any safety layer, any shared interface between the three pieces,
and version control.

That is the headline. Two good subsystems and no system.

## Housekeeping

- No git repo anywhere in the folder. `ballistics/.gitignore` exists but there is
  no `.git`. Everything else is loose files.
- `solver.rs` in the root is a byte for byte copy of
  `ballistics/crates/ballistics-core/src/solver.rs`. Delete it.
- `README (5).md` in the root is a byte for byte copy of `ballistics/README.md`.
  So the ballistics readme is sitting at the top of the turret project and the
  project has no readme of its own.
- `.338NM Ballistic Solver` starts with a dot, so it is hidden on Linux and gets
  skipped by find, globs and most tooling. It also has spaces. Rename it before
  any of this touches a Jetson.

## Rust ballistics core

Good code. Clean separation, honest comments, sign conventions documented, the
traits are the right traits. Findings ranked.

1. Feature regression vs the Python. Spin drift and Miller SG are in
   `stability.py` and gone from the Rust. On a .338 that is roughly 8 to 10
   inches right at 1000 yd. The readme lists it under "Next" but the Python
   already has it, so today the Rust build is the less accurate of the two.

2. No aiming API. This is the real integration blocker. Everything in the crate
   is a table keyed to a rifle zero: `zero_angle` then `flight` then rows in
   yards. Fire control needs the inverse. Given slant range, look angle, target
   relative motion and current air data, hand back bore elevation above the LOS,
   bore azimuth offset, and time of flight, in radians, one shot, no table.
   Right now the only front doors are the CLI and the wasm wrapper, and both are
   shooter facing. Nothing in the crate can be called by a control loop.

3. Hot path recomputation. `Solver::accel` calls `atmosphere.at()` on every
   evaluation, which is a `pow` plus an `exp`, and `Coriolis::acceleration`
   calls `omega()` every time, which is four trig calls. RK4 is 4 accel
   evaluations per step, so at dt = 1 ms and a 2 s flight that is about 8000
   sets of transcendentals per trajectory, all of it recomputing constants.
   Omega is fixed for the shot, put it in `Env`. Air only needs recomputing when
   the height moves a few meters. That is an easy 2x to 5x, and it matters as
   soon as an aiming solver has to run trajectories at 50 to 100 Hz. It matters
   a lot more on the STM32H7 target the readme names.

4. `table.rs` quietly ends the no_std story. The `table` feature pulls in std,
   and `impl std::error::Error` hardcodes it. Consistent today, but it means
   there is no serializable request/response path on the MCU build. If the
   embedded target is real, that needs an alloc or fixed capacity version.

5. `zero_angle` cannot go negative. Bracket is [0, 0.25]. Correct for a rifle
   zero, wrong for a turret that has to depress below the LOS. The aiming solver
   needs a bracket that spans negative elevation.

6. The Newton refinement in `Flight::next` is a soft spot. Landing on a station
   re-runs a full `rk4(s0, tau)` up to five times, and `if vr <= 0.0 { break }`
   silently accepts whatever it has. Worth a test at 45 degrees look angle and
   near apex.

7. Magic numbers in the termination test with no comment: `time > 120.0`,
   `v.norm() < 10.0`, `p.y < -10_000.0`. The 10 m/s one will cut a subsonic
   terminal trajectory short in some conditions. Make them named consts or
   fields on `Shot`.

8. Transonic interpolation is piecewise linear over a 0.025 Mach grid across the
   0.95 to 1.05 spike. Between M 0.95 (Cd 0.2054) and 0.975 (0.2993) linear
   under-predicts the knee. Either go monotone cubic over that band or write
   down that you accept 1 to 2 percent Cd error there, because the .338 goes
   transonic somewhere around 1400 to 1500 yd.

9. `reference.rs` has never actually run. `tests/fixtures/` holds only
   `_example.json`, which the test skips, so the Python cross-check passes
   vacuously. Three or four dumped loads is the cheapest high value item in the
   whole repo.

10. Speed of sound uses dry air gamma = 1.4 with a moist density. Small, but the
    crate is fussy about humidity everywhere else, so it is inconsistent.

## MATLAB gimbal controller

The plant math checks out. Pan inertia varies with tilt, the `Jpanp*thDot*psiDot`
and `0.5*Jpanp*psiDot^2` coupling terms have the right signs, gravity and the
energy function agree. Findings:

1. `NOISE_FREE = true` in both run scripts. Every PID vs LADRC number the project
   reports comes from a noise free plant, and the plant defines 0.5 deg/s gyro
   noise and 0.02 deg encoder noise that never get exercised. Turn it off and
   the comparison changes, because of the next item.

2. `CascadeController` differentiates the raw encoder. `dth = (th_meas -
   th_prev)/dt` at dt = 1 ms with 0.02 deg encoder noise is about 0.35 rad/s of
   noise on `dth`, times Kd_p = 0.3 puts roughly 0.1 rad/s of garbage straight
   into the rate setpoint, on top of an already noisy gyro. There is no filter
   anywhere in the loop. There is a gyro right there, it should not be
   differentiating position at all.

3. The stabilize attenuation metric is dimensionally wrong.
   `20*log10((rms*D2R)/(a_base/sqrt(2)))` divides a pointing angle in rad by a
   base rate in rad/s. The units come out as seconds and the dB number means
   nothing. Compare angle to angle, or report the transfer at the sway frequency.

4. The plant is more optimistic than what the design notes claim exists. No
   drivetrain compliance, no backlash, no LuGre (it is `b*w + tau_c*tanh`), no
   motor current loop, no back EMF or voltage limit, no encoder quantization, no
   gyro bias walk, no computation or actuation delay, no ZOH. The controller
   sees true state in the same tick it commands torque. Every one of those is
   where a real gimbal gets you at commissioning.

5. Base motion only enters through friction, `w - w_base`. That is right for an
   ideal bearing, but it leaves out the mass imbalance torque reacting to base
   linear acceleration, which is the dominant disturbance on a vehicle mount,
   and there is no cross axis kinematic coupling (base roll should show up in
   tilt as a function of pan angle). On a truck bed that is the whole problem.

6. `td_pan` and `td_tilt` read like time delays and are constant disturbance
   torques. Rename to `tau_d_pan` / `tau_d_tilt`.

7. Property blocks have no units. `J = 0.015`, `b = 0.02`, `mgl = 0.15` with the
   trailing comments stripped. Put the units and where the numbers came from.

8. `PIDRate` anti-windup tests `u == u_unsat` on floats. Works because `u` is a
   clamped copy, but use `abs(u_unsat) <= u_sat`.

## Python / React

It is the more complete ballistics model. Do not retire it until the Rust has
parity, and use it as the oracle for `reference.rs` on the way there.

- `main.py`: `n = int(max_range_yd // step)` drops the remainder, so 1600 yd at a
  30 yd step stops at 1590 with no 1600 row. Ranges also start at one step, so
  there is no muzzle row.
- CORS is `allow_origins=["*"]`. Fine on a laptop. Not fine on a networked Jetson.
- Once the Rust has parity the FastAPI backend goes away and React calls the wasm
  directly. The ballistics readme already lays that out and it is the right call.

## Integration plan

The gap is the middle. Ballistics produces tables for a person, the controller
takes a setpoint from a hand written scenario script, and nothing turns a target
into a setpoint. Layers in the order I would build them.

### Layer 0, repo hygiene

`git init` at the top. One repo:

```
turret-compute/
  ballistics/        rust workspace, as is
  ballistics-python/ renamed, kept as reference oracle
  control/           MATLAB reference plus the port
  fcs/               the fire control loop, new
  sim/               closed loop harness, new
  docs/
```

Delete the two duplicate files, drop the leading dot and the spaces, write a real
top level readme.

### Layer 1, the aiming API in ballistics-core

New module, `aim.rs`. Roughly:

```rust
pub struct Target {
    pub slant_range: f64,   // m
    pub look_angle: f64,    // rad, + up
    pub bearing: f64,       // rad, + right of the mount reference
    pub range_rate: f64,    // m/s, + opening
    pub cross_rate: f64,    // rad/s
}

pub struct Solution {
    pub elevation: f64,     // rad above LOS
    pub azimuth: f64,       // rad lead, + right
    pub tof: f64,           // s
    pub impact_speed: f64,  // m/s
    pub converged: bool,
}

pub fn aim<D, A>(solver: &Solver<D, A>, shot: &Shot, tgt: &Target) -> Solution;
```

Superelevation by the same bisection with the bracket widened to allow negative.
Lead by iteration: solve, get TOF, move the target forward, re-solve. Two or
three passes converge. Fixed iteration budget and a `converged` flag so the loop
stays hard real time.

Everything already built sits on top unchanged. CLI, wasm and the React app keep
using `table.rs`. This adds a second front door, it does not disturb the first.

Then hang spin drift and aerodynamic jump off `Solution` as post corrections,
which means porting `stability.py` for SG. Do the omega and air caching first so
one `aim` call fits in the loop budget.

### Layer 2, get the controller out of MATLAB

MATLAB stays as the design and tuning reference. Write the controller in Rust as
a fixed step, allocation free `step(setpoint, gyro, encoder, dt) -> torque`.
`PIDRate` and `LADRCRate` are already exactly that shape, so the port is close to
mechanical. Then run the same scenario file through both and diff the traces.
That diff is the regression test that keeps the Jetson code honest against the
model, and it is the thing that will catch a sign flip at 2am on a range.

### Layer 3, the missing middle

```
sensor -> IMM-EKF, target state in a stabilized frame
       -> aim(), superelevation + lead + TOF
       -> AimPoint { az, el, az_rate, el_rate, tof, valid }
       -> cascade controller, rate FF from the tracker velocity
       -> torque
```

The cascade already takes a rate feed forward argument, and the tracker velocity
estimate is what should be driving it. That is the whole integration, and it is a
one line handoff once `AimPoint` exists. Define that struct first and both sides
can be built independently.

### Layer 4, one closed loop sim

Right now the plant runs in MATLAB and the ballistics runs in Rust and nothing
runs both. A `sim` crate that closes the loop: synthetic target track, tracker,
aim, gimbal plant, pointing error at trigger pull, predicted miss distance at the
target.

That last number is the only one that matters and nothing in the project produces
it today. Pointing RMS in degrees is a proxy. Miss distance in inches at 800 yd
is the answer, and it is what makes the PID vs LADRC question decidable.

### Layer 5, hardware

Two things to decide now because they are expensive later.

Where the loop runs. A 1 kHz rate loop does not belong in Linux userspace on the
Orin, PREEMPT_RT or not. Put the rate loops on an MCU, the STM32H7 the ballistics
readme already names, and let the Jetson do tracker, ballistics and mission at 50
to 100 Hz. That splits `ballistics-core` cleanly, `aim` on the Jetson and the
no_std core available on the MCU if fallback ballistics is ever wanted.

Time. The whole thing is a time of flight prediction problem, so IMU, camera and
control need a common timebase. Pick one hardware sync line or PTP now.
Retrofitting timestamps later is miserable.

Safety. The arming and inhibit logic belongs in this repo next to the FCS with
its own tests, not bolted on at the end. There are safety invariant validators in
the design notes and none of it is in this folder.

## Order I would work it

Cheap and high value first.

1. git init, kill the two duplicates, rename the dotted folder, real top level readme.
2. Dump three or four loads out of the Python solver into `tests/fixtures/` so
   `reference.rs` actually runs. One afternoon, and it is the only thing standing
   between the port and a real correctness claim.
3. Flip `NOISE_FREE` to false, fix the encoder differentiation, fix the dB metric,
   re-take the PID vs LADRC numbers.
4. `aim.rs`. This is the keystone. Nothing downstream can start without it.
5. Spin drift and Miller SG in Rust, parity with Python, then retire FastAPI.
6. Perf: omega into `Env`, cache the air layer.
7. Port the controller to Rust, cross validate against MATLAB on the same scenario.
8. Plant fidelity: compliance, backlash, loop delay, quantization, base accel.
9. Bring the tracker in, close the loop in sim, report miss distance.
